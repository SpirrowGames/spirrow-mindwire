## 1. 背景

msg-6739 の背景を、言い換えずに写す。

- 開発機を拡張する。UE 機 2 台（5950X/3090 = VoxelWorld 用、Intel/RX9060XT 16GB = PlayProof 用 兼 CI・nightly）を愛媛に集約し、{{HOST_SERVICES}} は東京へ移設する。
- このまま各機に Conductor を置くと、スレッドの二重駆動と checkpoint の上書きが起きる。

### 1.1 根拠：調査で確認した事実（コード実読、msg-6739）

1. sweep はローカルの sweep.json 候補だけで駆動しており、サーバー側にスレッドの占有ロックはない。
2. checkpoint の保存キーは project×user×author で、スレッドを含まない。
3. Conclair の既読カーソルは project×identity×thread をキーにしている。
4. loop_control の HOLD はサーバー側にあり、全機に共通で効く。

## 2. 決定事項（D1〜D17）

msg-6739「決定事項」1〜17 を、条項番号 D1〜D17 として言い換えずに写す。ただし D6 は 2026-10-13 に、D12 は 2026-10-14 に、takahito の指示で改訂した（改訂前の文言はそれぞれの直下に残す）。

- **D1. 中央 1 Conductor ＋ 実行機プール。** tomtebo も実行機の 1 台として扱い、特別扱いしない。実行機台帳を置かない状態が、現行の単機構成と完全に同じ動作になること。前例は owner_map の「キーがなければゲート OFF」と同じ流儀。
- **D2. 能力による振り分け。** 実行機は capabilities（例: `ue`）、slots、clones（project→clone パス）、wol を持つ。repo_dir は sweep の候補から外し、実行機側の clones に移す。ターンの要件 `requires` は、候補ごとの静的な宣言を既定とし、handoff で上書きできる枠を最初から用意する（Bohr の reproduce-first のターンでも UE が要る場合があるため）。
- **D3. 実行機の選び方。** 起きていて空きスロットがある → 同じスレッドの前回の実行機（速度のための優先で、必須ではない）→ 空きの多い機械、の順。全員寝ていれば WoL で 1 台だけ起こす。
- **D4. オフライン時の二段構え。** WoL ゲートウェイで起こして実行し、失敗したら park して停止理由に「実行機オフライン」を明示する。
- **D5. ターン途中で実行機を喪失した場合。** 自動では再試行せず、park（「実行機喪失」）。依頼を受け取る前の失敗だけは、別の機械へ回してよい。
- **D6. 実行機台帳は Conductor の設定、動的な報告・ターン依頼と占有権・予約は Magickit、Conductor だけが使う状態は Conductor のローカルに置く。** 今回の設計で Conclair への新しい依存は作らない。（2026-10-13 takahito 指示により改訂 — msg-6854。改訂案 Bohr msg-6890・msg-6892）
  - 改訂前の文言（msg-6739）: 「ターン依頼・占有権・実行機台帳・死活状態・現バージョンは Conclair に置く。Magickit はオーケストレーションに専念する。」
  - 置き場所の内訳は §2.2 に固定する。
- **D7. git 同期はプログラムで行い、LLM のルールにしない。** オプションで既定は OFF（`[turn.git] sync`）。
  - ターン前: fetch（＋必要なら lfs pull）→ 未コミット変更があれば park → スレッドブランチを fast-forward のみで追従（ローカルが先行していれば park）
  - ターン後: 未コミット変更があれば park → スレッドブランチを push（失敗は park）
  - 自動コミットや stash はしない。main / develop へは構造上 push できないようにする。
- **D8. ブランチ名は機械的に決める。** `loop/<thread_id>`（小文字に正規化、長さ上限を超えたら末尾をハッシュ化）。merge 済みなら `-2`, `-3` と連番で切り直す。進行中の既存スレッドは上書き指定で現行のブランチ名を維持する。
- **D9. 秘密情報は各実行機が起動時に Vaultwarden（bw CLI）から取得する。** bootstrap 用の鍵は Windows 資格情報マネージャーに置く。取得できなければ、はっきり止まる（前回値のキャッシュで動き続けない）。
- **D10. バージョンは git の不変タグを正とする。** セマンティックバージョンで、タグは動かさず新規作成していく（`executor/vX.Y.Z`、注釈付きタグ）。ロールバックは「古いコミットに新しいタグを作る」前進操作。`executor/*` は GitHub ルールで削除・更新を禁止し、作成は Magickit のデプロイ経路のみに限定する。メジャーは Conductor⇔実行機のプロトコル非互換を表すが、当面は完全一致で照合する。
- **D11. 実行機は tick 冒頭で最新のタグと自分のバージョンを比べ、遅れていれば sync-repo してから依頼を受け付ける**（pull 型の追従）。実行機の処理は Conductor と同じく tick ごとに起動して終わる単発型にし、自己更新の問題を回避する。依頼にはタグ名を載せ、不一致なら拒否して park（「実行機バージョン不一致: 手元 X / 依頼 Y」）。
- **D12. 切り替え時刻は mindwire（実行機）が記録主体となり、Magickit の deploy_history に「どの機械がいつ切り替わったか」を報告する。** 実行機の現バージョンは Magickit にある動的な報告（§2.2）の一項目として持ち、報告は毎 tick 上書きされるので履歴は持たない。切り替えの履歴は deploy_history だけが持つ。Conclair は実行機のバージョンを持たない。（2026-10-14 takahito 指示により D6 に合わせて改訂）
  - 改訂前の文言（msg-6739）: 「切り替え時刻は mindwire（実行機）が記録主体となり、Magickit の deploy_history に「どの機械がいつ切り替わったか」を報告する。Conclair は現バージョンだけを持ち、履歴は持たない。」
- **D13. 利用予約。** 人が UE 機を使うときは、Claude のセッションから予約できる MCP ツール（予約・延長・解除）を Magickit に用意する。予約中は新しい依頼を振らず、実行中のターンは最後まで終わらせる。人は解除を忘れる前提なので、予約には必ず期限を付けて自動で失効させる。
- **D14. CI との共存。** 最終形は CI の仕事も実行機の依頼として流す（b）。段階的に、まずは self-hosted runner のジョブの開始・終了に合わせて受付停止を切り替える（a）。
- **D15. 移設からフェーズ 1 完成までは、ループは tomtebo の Conductor 1 本で回す。** UE 機は人の手作業と CI だけに使う。この順序なら、暫定の修正（host 付き sweep.json、checkpoint の改修）はどちらも不要になる。
- **D16. 単一スレッドの分割禁止（9/5 裁定）と、「1 プロジェクトにつき同時に動く Heisenberg は 1 本」を、中央スケジューラの制約として実装する。**
- **D17. 投稿のメタデータに実行機名を載せる。**

### 2.1 決定の解釈（D 本文は改訂した D6・D12 を除き逐語のまま変えない。実装はこの節に従う）

D1〜D17 は承認済みの文言をそのまま残す（D6・D12 は takahito の指示による改訂後の文言）。そのうえで、文言だけでは動作が一意に決まらない箇所について、実装が従う解釈をここに固定する。解釈と D 本文が食い違って見える場合は、この節が実装の正である。

- **D7「ターン前: 未コミット変更があれば park」の止まる単位は clone である。** ターン前に未コミット変更（または途中の git 操作・HEAD の移動）を検出したら、ターンは開始しない。止める主体は clone guard（exit 8）で、止まるのは「その clone への dispatch」であり、これから dispatch されるスレッドを park 状態にはしない（§6）。前のターンが残した汚れはそのスレッドの責任ではなく、汚した張本人のスレッドはターン後の検査（D7「ターン後: 未コミット変更があれば park」、`git.dirty_after_turn`）ですでに park されているためである。「黙って止まらない」という D7 の意図は、exit 8 の通知経路で満たす。設計 v1 B-3(1)（Einstein msg-6761 で支持）。
- **D7「ローカルが先行していれば park」は、スレッドを park する（上の clone 単位の停止とは扱いが違う）。** 比べる対象はそのスレッド専用のブランチ（D8 の `loop/<thread_id>`、または override で登録されたそのスレッドのブランチ）であり、default branch や他のスレッドのブランチではない。ある clone のそのブランチにだけある未 push のコミットは、同じスレッドの以前のターンがその clone（その実行機）で作り、push できなかったものである。その時点でそのスレッドは、ターン後の検査（`git.push_failed`）ですでに park されている。したがって「前のターンが残した汚れは、これから dispatch されるスレッドの責任ではない」という上の原則は当てはまらない。ここで park せずに clone 単位で止めると、そのスレッドの成果が 1 台の clone に取り残されたまま、別の実行機で古い状態からターンが進み、分岐を作る。ただし、この検査が見えるのは自分の clone の状態だけである。未 push のコミットを持たない別の実行機では、ローカルとリモートが一致するのでこの検査は通ってしまう。プール環境でこれを防ぐ仕組みは §7 (e) に定める（単機の単位 1 では clone が 1 つなので、この検査だけで足りる）。分岐（`git.diverged`）も同じ理由でスレッドを park する。default branch そのものの汚れや HEAD の位置のずれ（どのスレッドにも属さない状態）は、clone guard の側で clone 単位に止める。
- **D11「不一致なら拒否して park」は、拒否するのは実行機、park を決めるのは Conductor、と主体を分ける。** タグ作成直後には、実行機と Conductor がそれぞれ自分の tick で新しいタグに追従するまでの間、両者のバージョンが一時的にずれる窓がある。この窓で生じる不一致は配備の通常動作であり、スレッドを park してはならない。単位 4 は次を満たすこと（§7 (c)）。
  - Conductor は、Magickit にある実行機の動的な報告の現バージョン（D6・§2.2）が依頼に載せるタグと一致する実行機だけを振り分けの候補にする。一致しない実行機は、その tick では「空きスロットがない」のと同じく候補外とする（D3）。
  - **実行機は、どの場合もスレッドを park しない。** 依頼の受け付け時に不一致を検出したら、理由を問わず（配備の窓・追従できないタグ・その他）依頼を拒否し、依頼を受け取る前の失敗（D5「依頼を受け取る前の失敗だけは、別の機械へ回してよい」）として Conductor に返す。拒否の記録には「実行機バージョン不一致: 手元 X / 依頼 Y」を載せる。
  - **実行機自身の追従の失敗は、実行機の障害として扱う。** tick 冒頭の sync-repo が失敗した場合、またはタグが実行機から見えない場合、その時点ではまだ依頼を受け取っていないので、スレッドは関係しない。実行機はその tick の依頼を受け付けず、失敗を Magickit への動的な報告（D6・§2.2）に載せて大きく通知する。Conductor はその実行機を候補から外す（D3）。
  - **park は Conductor だけが決める。** Conductor はスレッドごとに nullable なタイムスタンプ `no_match_since` を 1 つだけ、Conductor のローカル状態に持つ（§2.2）。tick ごとに、プールの中に依頼のタグと一致する実行機が 1 台もなければ、`no_match_since` が空ならその時刻を入れ、1 台でもあれば空に戻す（区間の累積や一時停止はしない。リセットだけである）。一致する実行機が 1 台でもあれば、それが空きスロットなし・予約中（D13）・実行中のどれであっても、その待ちは通常の資源待ちであり、バージョン不一致としては数えない（資源待ちの扱いは D3・D4・D13 と単位 5 の公平性に従う）。`now - no_match_since` がこの上限を超えた場合に限り、Conductor がそのスレッドを park し、停止理由に「実行機バージョン不一致: 手元 X / 依頼 Y」を明示する。X はその時点のプール内の実行機の現バージョン（複数あれば列挙）で、定義上 Y を含まない。これは D4 の「実行機オフライン」と同じ構造（振れる実行機がない → 一定の手当ての後に park）であり、D5 の「依頼を受け取る前の失敗は別の機械へ回してよい」とも矛盾しない。上限時間は未決の数値とする（§5）。起点をスレッドや依頼の作成時刻にしてはならない。長く資源待ちをしていたスレッドが、配備の窓で一致する実行機が一瞬 0 台になっただけで即座に park されてしまい、この節が防ごうとしている誤った park が起きるからである。
- **D12 は D6 に合わせて本文を改訂済み（§2）。** 改訂前の「Conclair は現バージョンだけを持ち」は D6 の改訂と矛盾していたため、読み替えではなく本文を書き換えた。
- **D17「投稿のメタデータに実行機名を載せる」は、投稿本文末尾の `<!-- source: … -->` フッターに載せる。** Conclair 側の変更は要らない（Bohr msg-6890 §2）。

### 2.2 状態の置き場所（D6 の内訳、2026-10-13）

mindwire の中で閉じられるものは閉じ、機械をまたいで共有しなければならないものだけを Magickit に置く（takahito msg-6854）。mindwire の中だけで共有の置き場所を持つ案（Conductor の機械に受け口のサーバーを置く、git リポジトリを状態置き場にする、Conductor が ssh で実行機のターンを同期実行する）は採らない。理由は Bohr msg-6890 §1 のとおりである（常駐プロセスが要り D11 の単発型の前提が崩れる、占有権の取り合いが push の競合になる、接続断でターンが死にフェーズ 2 の並列化もできない）。

| 種類 | 中身 | 置き場所 | 誰が読むか |
|---|---|---|---|
| 静的な定義（実行機台帳） | 実行機名・capabilities・slots・扱える project の一覧・wol（MAC とゲートウェイ） | Conductor の設定ファイル（`[executors.<name>]`） | Conductor だけ |
| 動的な報告 | 起きているか・現バージョン・空きスロット・project ごとの clone の状態（`clone_dirty` を含む）・追従の失敗 | Magickit（実行機が毎 tick 全量を上書き、古くなれば失効） | Conductor |
| 実行機ローカルの設定 | 自分の実行機名と、project → clone パスの対応だけ | 各実行機 | その実行機だけ |
| ターン依頼・占有権 | remote の実行機に渡すターン | Magickit | Conductor・実行機 |
| 利用予約（D13） | 予約・延長・解除と期限 | Magickit | Conductor |
| Conductor だけが使う状態 | `no_match_since`、`stranded_sha` と `stranded_on`、スレッドごとの前回の実行機（D3） | Conductor のローカル状態 | Conductor だけ |
| 実行機名（D17） | 投稿した実行機 | 投稿本文末尾の `<!-- source: … -->` フッター | 読み手 |
| 投稿・checkpoint・既読カーソル・loop_control の HOLD | 現行のまま | Conclair | 現行のまま |

- **台帳と報告に同じ情報を二重に持たない。** capabilities・slots・wol は台帳だけが持ち、報告には含めない。clone パスは実行機ローカルの設定だけが持ち、台帳は project 名しか知らない。
- **`stranded_sha` と `stranded_on` は、実行機がターン結果として返し、Conductor がローカル状態に記録する。** 読み書きするのは中央の Conductor 1 本だけなので、共有の置き場所は要らない。
- Conclair に置くものは現行から増やさない。

## 5. 未決の数値（計測してから決める）

以下は本 ADR では**未決**とする。値を決めるときは、計測結果を添えて本 ADR を改訂する。

- 全体の同時実行数の上限と slots の値（3 台時の Claude Max 20x の消費を計測してから）
- 死活確認の間隔と WoL の起動待ち時間（UE 機の起動時間を実測してから）
- 予約の既定の期限
- バージョン一致待ちの上限時間（§2.1 D11 の解釈。配備で全実行機が追従し終えるまでの実測時間から決める）

## 6. 単位 1 の既知の制約

- ターン後に clone を汚したまま終わると（未コミット変更、途中の git 操作、HEAD の移動）、汚したスレッドは `git.dirty_after_turn` / `git.head_moved` で park されて通知される。その clone は、オペレーターが片付けるまで dispatch を受け付けない（clone guard の exit 8）。
- 自動で片付ける（stash / reset / clean）ことは D7 と clone guard の方針「検出して拒否、片付けない」で禁じられている。
- この影響範囲は、単機運用の現在と同じである。プール環境での影響範囲の縮小は、次節の単位 4 への要件で扱う。
- ターン前に clone が汚れていた場合は、clone guard（exit 8、隔離なし）に任せ、これから dispatch されるスレッドは park しない。前のターンが残した汚れは、そのスレッドの責任ではないためである。これは D7「ターン前: 未コミット変更があれば park」の解釈であり（§2.1）、ターンは開始せず止まるが、止まる単位はスレッドではなく clone である。

## 7. 単位 4 への要件

- **(a) clone 単位で外す。** Magickit にある実行機の動的な報告（§2.2）に、project ごとの clone の状態として `clone_dirty` を持たせる。スケジューラ（D3）は、汚れを検出した「実行機 × clone」の単位で候補から外し、他の実行機に振る。実行機全体は外さない。
  - **`clone_dirty` は、依頼があるかどうかに関係なく、実行機が tick ごとに書き直す。** 実行機は tick ごとに起動して終わる単発型である（D11）。tick の冒頭、依頼を受け付ける前に、自分の clones に登録されたすべての clone に clone guard と同じ検査（未コミット変更、途中の git 操作、HEAD が default branch にない）をかける。その結果を、起きていること・現バージョン・空きスロットと合わせた動的な報告の全量として Magickit に送る。報告は前回分を丸ごと上書きする（差分の更新や、汚れたことを覚え続ける形にはしない）。汚れていれば立て、きれいなら下ろす。
  - 依頼が来たときにだけ検査する方式にはしない。候補から外された clone には依頼が来ないので、その方式だと一度立った `clone_dirty` が二度と下りなくなる。tick ごとに書き直していれば、オペレーターが手で clone を片付けた後の最初の tick で `clone_dirty` が下り、次の振り分けから候補に戻る。
  - 実行機が起きていない間（tick が回らない間）は、`clone_dirty` を含む報告の全体が、死活確認（§5 の間隔）によって古いものとして扱われる。報告が死活確認の間隔より古い実行機はオフライン扱いにし、`clone_dirty` の値によらず「すぐ振れる実行機」の候補から外す（D3・D4）。古い「きれい」を信じて振ることはしない。オフライン扱いの実行機を WoL で起こすかどうかは、台帳で判断する（§7 (f)）。
  - 書き直しは検査結果を写すだけで、clone を片付けることはしない（§6。stash / reset / clean はしない）。
  - 単位 4 のテストで次を固定する。汚れた clone が候補から外れること。依頼が 1 件も来ない状態でオペレーターが手で片付けると、次の tick の報告で `clone_dirty` が下りて候補に戻ること。報告が死活確認の間隔より古い実行機はオフライン扱いになり、古い報告が「きれい」でも振られないこと。
- **(b) スレッドごとの worktree（再提案の候補）。** スレッドごとに git worktree を分けて汚れを隔離する案は、単位 4〜5 で再提案する候補として記録する。D2 の「clones = project→clone パス」を変更することになるので、採用するときは改めて提案する。
- **(c) 配備の窓でバージョン不一致による park を起こさない。** §2.1 の D11 の解釈に従う。振り分けは Magickit の動的な報告の現バージョンが依頼のタグと一致する実行機に限り、実行機は不一致の依頼を拒否して依頼前の失敗（D5）として返すだけで、スレッドを park しない。実行機の追従失敗は実行機の動的な報告に載せ、Conductor が候補から外す。park は Conductor が「バージョン一致待ちの上限時間」を超えたときだけ決める。単位 4 のテストで、「新しいタグの作成直後に、旧タグの依頼が実行機に届く」ケースで park されないこと、実行機の sync-repo が失敗してもスレッドが park されないこと、上限時間を超えて初めて Conductor が park すること、タグの一致する実行機が満杯または予約中のあいだは上限時間を超えて待っても park されないこと、を固定する。
- **(d) 実行機台帳がない状態も、同じ選択の経路で扱う。ただし、ターンを渡す手段は実行機ごとに分ける。** 1 本にまとめるのは、実行機を選ぶ処理（要件・バージョン・空き・予約・`clone_dirty` による絞り込みと D3 の順位付け）である。D1 の「実行機台帳を置かない状態が、現行の単機構成と完全に同じ動作になること」を、この選択を通らない別の選択経路で満たしてはならない。台帳（Conductor の設定の `[executors]`、§2.2）がないときは、Conductor が自分の機械 1 台だけを持つ暗黙の台帳（capabilities = すべての要件を満たすワイルドカード `*`、slots 1、clones は現行の sweep 候補の repo_dir、wol なし、送り方 = local）を内部で組み立て、同じ選択の処理に通す。capabilities をワイルドカードにするのは、台帳がない現行の構成では候補がすべて無条件にローカルで実行されるためである。`requires` を宣言した候補（D2）も、暗黙の実行機に必ず合致する。capabilities を空にすると、`requires` を持つ候補が一度も振られずに残り、INV-0 に反する。ワイルドカードは暗黙の台帳だけが使える値とし、明示的に設定した台帳では受け付けない（設定時に拒否する）。
  - 選ばれた実行機にターンを渡す手段は、実行機ごとの送り方で決める。**local**（Conductor 自身の機械）は、現行どおりその tick の中で同期的にターンを実行する。**remote** は、Magickit のターン依頼（D6・§2.2）に載せ、その実行機が自分の tick で取りに来る。
  - 台帳がない状態に現れるのは local の実行機 1 台だけである。だから、依頼を取りに来る別プロセスがないまま依頼が積まれて止まる、ということは起きない。
  - 暗黙の台帳の実行機は、Magickit に動的な報告を送らない。Conductor が同じ tick の中で直接 clone guard の検査結果を見て、選択の処理に渡す。台帳がない状態では、Magickit への依存も一切生じない。
  - 現行と同じ動作になること（同じ tick で同期実行され、Magickit へのターン依頼も動的な報告も 1 件も作られないこと、`requires` を宣言した候補も振られることを含む）を INV-0 のテストで固定する。
- **(e) 未 push のコミットが取り残されたスレッドは、コミットを持つ実行機でだけ回復させる。** 未 push のコミットはそれを作った clone にしかないので、別の実行機のターン前検査（ローカル先行の検査）では見えない（§2.1）。単位 4 は次を満たすこと。
  - **記録。** ターン後に `git.push_failed` で park するとき、実行機は、push できなかったブランチの先端のコミット（`stranded_sha`）と実行機名（`stranded_on`）をターン結果として Conductor に返し、Conductor がそのスレッドの状態としてローカル状態に記録する（§2.2）。ターン前に `git.local_ahead` で park するときも、同じように返して記録する。
  - **振り分け。** `stranded_sha` が記録されているスレッドは、Conductor が `stranded_on` の実行機にだけ振る。これは D3 の「前回の実行機」優先とは違い、必須の条件である。その実行機に振れない場合は、D4 と同じ扱いにする。WoL で起こしても起きなければ「実行機オフライン」で park し、停止理由に `stranded_on` を明示する。
  - **ターン前の回復（`stranded_on` の実行機のとき）。** fetch した後で、ローカルのスレッドブランチの先端が `stranded_sha` と一致し、かつリモートのブランチがその祖先であれば、ターンを始める前に、ターン後と同じ push（`ThreadBranch` の型ガードを通し、refspec を明示し、`--force` は付けない）を 1 回だけ試みる。
    - 成功したら、記録を消して通常のターン前の手順を続ける。この時点でローカルとリモートは一致しているので、ローカル先行の検査も通る。
    - 失敗したら、`git.push_failed` で再び park する（記録は残す）。
    - 先端が `stranded_sha` と一致しない場合、またはリモートが祖先でない場合は、何を push するかを機械的に決められない。従来どおり `git.local_ahead` または `git.diverged` で park する。
    - D7 の「ローカルが先行していれば park」のうち、push 失敗の記録と完全に一致する場合だけを、この回復で置き換える。それ以外の場合は変えない。
    - これにより、park を解除して同じ実行機に振れば、オペレーターが手で push しなくても回復できる。ターンを始められないまま、ターン後の push にも到達しない、という行き詰まりは起きない。
  - **ターン前の安全網（`stranded_on` 以外の実行機のとき）。** 振り分けの誤りなどで、ほかの実行機にスレッドが届いた場合を考える。fetch した後に、リモートのスレッドブランチが `stranded_sha` を含まなければ、その実行機はターンを始めず、スレッドを `git.stranded_commits` で park する。停止理由には `stranded_on` を明示する。
  - **含むかどうかの判定。** 先に `git cat-file -e <stranded_sha>^{commit}` でオブジェクトがあるかを確かめる。
    - ない場合は「含まない」と判定する。コミットを作っていない実行機では、これが通常の結果である。
    - ある場合は、`git merge-base --is-ancestor <stranded_sha> <remote>/<branch>` を実行する。終了コードが 0 なら「含む」、1 なら「含まない」と判定する。
    - それ以外の終了コード（128 など）は、git の異常として `git.branch_resolve_failed` で park する。例外として外に出してはならない。
  - **記録を消す時点。** リモートのスレッドブランチが `stranded_sha` を含むことを実行機が確かめ、その結果をターン結果として返した時点で、Conductor が記録を消す。オペレーターが手で push した場合も、次のターン前に消える。
  - **テスト。** 単位 4 のテストで次の 4 つを固定する。
    - 「A で push 失敗 → park → 解除 → A に振られる」とき、ターン前の push で回復してターンが進むこと
    - 同じ経路でターン前の push も失敗するとき、`git.push_failed` で再び park されること
    - 「B に届く」とき、B がターンを始めずに `git.stranded_commits` で park されること（コミットのオブジェクトが B にない場合を含み、例外にならないこと）
    - `stranded_on` の実行機がオフラインのとき、「実行機オフライン」で park されること
- **(f) 静的な台帳と動的な報告を突き合わせて選ぶ。** 振り分けと WoL の判断は、Conductor の設定にある台帳（§2.2）を起点にし、Magickit の動的な報告を重ねて行う（Bohr msg-6892。Einstein msg-6891 の指摘への対応）。報告が失効しても台帳は Conductor の手元に残るので、寝ている機械は「台帳にあるが報告がない」状態として見える。
  - 要件（`requires`、D2）の判定は台帳の capabilities で行う。報告が失効した実行機でも判定できる。
  - 全員寝ていれば、台帳の wol で 1 台だけ起こす（D3・D4）。起こしても起きなければ「実行機オフライン」で park する（D4）。
  - 台帳にない実行機名から報告が来たら、その報告は使わず、はっきりログに残す。
  - 台帳ではその実行機が扱う project なのに、報告にその project の clone がない場合は、その「実行機 × project」を候補から外し、そのことを報告する。黙って振らない。
  - 台帳がない場合（`[executors]` なし）は §7 (d) の暗黙の台帳になり、この突き合わせは行わない。
  - **テスト。** 単位 4 のテストで次の 3 つを固定する。
    - 報告が失効した実行機を、台帳の capabilities で選び、台帳の wol で起こすこと
    - 台帳にない名前からの報告は使われず、ログに残ること
    - 台帳の project に対応する clone の報告がない場合、その「実行機 × project」が候補から外れ、そのことが報告されること
